# 開発者向け録音レイテンシー診断（ローカル実装）

STUDIO 11の補正ロジックを維持した診断機能。今回は公開・push・デプロイなし。

## 入口

ローカルサーバーを起動する：

```sh
python3 -m http.server 4173 --bind 127.0.0.1 --directory dist
```

- 専用の測定画面：`http://localhost:4173/diagnostics.html`
- 普段の制作フローを観測：`http://localhost:4173/?diagnostics=1`
- 通常画面：`http://localhost:4173/`。診断ロガーをロードせず、開発者向けリンクも表示しない。

`diagnostics=1`の制作画面では、停止後の録音診断を専用ログへ保存する。プロジェクトメニューから専用診断画面へ移動できる。録音中には移動しない。診断機能を使わないURLで後から変更したクリップの位置・手動補正は観測できないため、診断画面の値は「最終観測値」。

MacのlocalhostはMac自身を指す。iPhoneのSafariからMacのlocalhostへは接続できない。また、通常のLANのHTTPアドレスではiPhoneがマイクを許可しない。iPhone実機は、承認後に用意する別のHTTPS検証URL等で確認する。今回、既存公開デモは更新していない。

## クリック測定の手順

1. 出力を「Apple有線EarPods」に設定。端末・USB-C/Lightning/変換アダプター・マイク位置をメモする。
2. マイクを接続し、実際の入力名と設定を確認。入力を変更する場合は選択後に接続し直す。ブラウザ既定は本体マイクとは限らない。通常制作画面の「自動」は本体優先なので、測る経路を一致させる。
3. EarPodsを耳から外し、片方の発音部を実際の入力マイクに近づけて固定する。EarPodsマイクならそのマイク、本体入力なら本体マイクを使う。小さめのシステム音量から始める。
4. 2つの確認欄をチェック。「短いクリックで測定可否を確認」を押す。約6秒で3か所のクリックを照合する。
5. 検出できない場合は測定不可。遅延0msとして扱わない。入力・位置・音量を見直す。別のスピーカーで測った値をEarPodsへ流用しない。クリックを拾える物理的配置が作れない環境では、この方法では正確なEarPods測定はできない。
6. 検出に成功したら、15秒×5回か4分×5回を選び、5回測定する。時間を変更した場合も音響結合を確認し直す。15秒版は長時間のドリフトの確認にはならない。
7. 先頭・中盤・終盤の差、平均、標本標準偏差、最小・最大を確認。「診断JSONを保存」で情報を取り出す。測定結果を自動補正には適用しない。

5回は同一Context・同一マイクで連続測定する。通常録音のテイク間でのContext再生成・マイク再接続の測定とは異なる。初回起動・再接続時の問題は`?diagnostics=1`の制作画面で別に観測する。

実際の出力装置名・音の経路はSafariのAPIだけでは保証できない。出力は自己申告として記録し、実入力名は取得範囲で記録する。音響結合が確認できたことは、APIが「EarPods」を検証したことを意味しない。

## 記録内容

- Context識別子、状態、サンプルレート、音声セッション、出力タイムスタンプ。
- マイク名と`getSettings()`。input/output/base latencyは取得可否と数値を分離。実際の0msは0.00ms、未取得・不正値は「取得不可」。
- 補正計算に実際に渡した報告値と合計、準備時・開始時・終了時のスナップショット。
- タップ時刻、録音開始要求のContext時刻、最初のPCMブロック時刻、再生予約時刻、保存開始位置。
- 既存の自動補正適用値、0.5秒超で破棄されたか、開始差の範囲外破棄、手動補正ms。
- クリック測定では、元のクリックとの正規化相関、検出信頼度、複数候補、音割れ、開始・中盤・終盤の遅延、同一条件の5回集計。

最初のPCM時刻はWorkletが受け取ったブロックの時刻。マイクで物理的に音が発生した瞬間ではない。APIのlatencyは端末報告値であり、クリックの実測値とは分ける。

通常録音と測定のどちらも、既存の`takeOrigin()`と上限処理は変更していない。専用測定では補正前PCMを予定時刻と比較する。既存補正を仮に適用した場合の残差はJSONの`predictedLegacyResidualSeconds`で確認できるが、音声には適用しない。

## 検出方式と無効判定

- 約18msの決まったノイズクリックを使用。参照波形と録音を約12kHzへ間引き、正規化相互相関をWorkerで計算する。
- 検索範囲は−50〜＋1500ms。範囲外・低い相関・小さすぎる入力・複数の有力候補・音割れは無効。
- 3か所すべての検出を要求する。失敗した回は平均に入れない。5回未完了の集計は暫定表示。
- 画面移動、Context中断、入力設定変更、検知できた機器変更、中止では測定を無効化しマイクを解放。出力経路だけの変更はAPIで検知できない場合があるため、測定中は機器・音量・位置を変えない。
- 相関の閾値や間引き後の精度がEarPods実音で十分かは未検証。実機で検出できない場合は、まず音響結合と信号品質を確認する。検出閾値を理由なく下げない。

## データの保護

専用画面はプロジェクト用IndexedDBを開かない。診断メタデータだけを別のlocalStorageキーへ保存する。

- `pocket-booth-developer-recordings-v1`：通常録音の観測ログ、最大30件。
- `pocket-booth-developer-measurements-v1`：クリック測定組、最大10組。出力条件ごとに別の組として保持。

診断ページのJSONには音声を含めず、外部送信しない。測定音声と参照クリックのプレーヤーは最新1回分だけをメモリ内に保持する。ページ終了時に解放する。診断ログ削除は上の2キーだけを消し、曲の保存領域を変更しない。

診断ログが保存できなくても本番テイクの保存を妨げない。測定ページでは保存失敗を表示し、JSONを直接取り出せる。

## 自動テスト

```sh
node --test tests/*.test.mjs
```

追加ユニットテスト：取得不可と0、既存補正式との一致、0.5秒上限、例外隔離、正負極性・音量変化、既知遅延、無音・雑音・二重候補・音割れ、集計、4分の合成PCMでの10msドリフト。

ブラウザテストにはPlaywrightとChromiumが必要。環境に合わせてモジュールとブラウザのパスを指定する。

```sh
SITE_URL=http://127.0.0.1:4173 \
PLAYWRIGHT_MODULE=/path/to/playwright/index.mjs \
CHROMIUM_PATH=/path/to/chromium \
node tests/browser-latency-diagnostics.mjs
```

この環境ではPlaywrightが`/opt/codex/cua_node/lib/node_modules/playwright/index.mjs`、Chromiumが`/usr/bin/chromium`。

ブラウザ試験は意図的な120msデジタルループバックで5回測定。iPhone・EarPodsの測定ではない。既存の`browser-audio-lifecycle.mjs`と`browser-timing.mjs`も併用する。

## 実機で未確認の項目

- iPhone Safariで表示される入力名・latency・出力タイムスタンプ。
- 実際のEarPodsの発音部と選択中マイクでクリックを拾えるか。
- 音響経路による波形変形があっても検出できるか。
- 実機での5回の平均・ばらつき、4分×5回のドリフト・発熱・メモリ。
- iOSの割り込み・ロック・抜き差し・ホーム画面版。
- 初回・準備済み・2回目以降の録音の違い。

次は実機のJSONを確認し、報告値不足・既存上限破棄・録音開始差・経路変化のどれが主因かを絞る。その後に限って補正ロジックの変更案を作る。今回、一律補正や自動校正値の適用は追加しない。

中断系ブラウザ試験：同じ環境変数で`node tests/browser-latency-interruptions.mjs`。許可待ち中のキャンセル、遅れて届くマイクの解放、機器変更・画面非表示・Context停止の模擬、320px幅を検証する。これらもiOS固有の実挙動を保証する試験ではない。
